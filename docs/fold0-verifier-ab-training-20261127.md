# 공식 재표집과 실사 대비쌍의 후속 검증기 A/B

기존 공식 모델의 216장 예측과, 이미 동결한 102개 공식 앵커 재판독 요청을 두 조건에 똑같이 사용한다. 새 학습은 Fold 0·4와 확인된 교차 장면의 훈련 그룹 3개를 제외한 공식 풀 안에서만 이뤄진다. 개발 분할과 현재 v2는 그대로 유지한다. 이 실험의 일차 질문은 **같은 후보를 제시받았을 때 실제 대비쌍이 수락·거절을 개선하는가**다.

## 실험과 승인 경계

- 데이터 작성자의 최종 승인 공식 실사 쌍만 입력한다. AI 보조 판독, 합성·외부 사진, 재압축 변형 및 미승인 쌍은 첫 비교에 투입하지 않는다.
- 같은 양성 앵커와 동일한 후보 질문·응답 형식을 사용한다. B의 음성은 승인된 실제 대비쌍이다. A의 음성은 같은 공식 코드 부재·출처·장면 상태 조건의 일반 예제에서 고정 해시로 고른다. 같은 그룹이 가능하면 먼저 사용하며 한 arm 안에서 음성 사진을 중복하지 않는다. OOF를 A 대조 선별이나 B 승인에 사용하지 않는다.
- 음성은 제시된 후보 코드에 대한 거절만 감독한다. 다른 위험이 보이더라도 전체 장면을 무위험으로 다시 라벨링하지 않는다. 양성은 같은 공식 위험의 근거·조치를 사용한다.
- 기존 v2는 보호 폴드와 확인된 교차 장면 훈련 그룹을 학습했으므로 어느 쪽의 부모에도 쓰지 않는다. 현재 실행 경로는 같은 공식 기반 모델에서 LoRA를 독립 초기화한 verifier-only 적응이다. 같은 시드에 생성한 초기 LoRA 텐서 지문이 일치하는지 대조한 뒤 학습한다.
- 승인 쌍이 1~3개면 서로 다른 음성 조건을 만드는 소수쌍 탐색 파일럿으로 진행하고 일반화 판정을 보류한다. 이 경우 누적 1, 네 쌍 이상이면 누적 4를 사용한다. 각 조건은 최소 2에폭이며, optimizer call 12회 이상에 필요한 에폭 수만 사용한다. 실제 LR이 0인 첫 호출은 따로 확인한다. 승인 쌍이 0개면 두 조건에 넣을 서로 다른 예제를 구성할 수 없다.

## CPU preflight 및 최소 GPU 경로

새 승인 쌍 JSONL의 독립 SHA를 입력받아 CPU에서 양쪽 계약을 만든다. 그 계약 SHA와 입력·모델·프롬프트 지문을 고정한다. 실제 로컬 Qwen processor와 trainer의 weighted encoder로 감독/결정 토큰·시각 토큰 및 optimizer-step 예제 수를 기록한다. 감독·결정 예산 차이는 동결 허용차(초안 기본 5%)와 대조한다. 시각 토큰과 자연어 길이 차이는 기록하고, 매 호출 단위의 양쪽 정확 일치를 요구하지 않는다. 성공한 preflight와 같은 계약이어야 로컬 GPU 경로가 열린다. 실제 훈련 결과의 solver call·LR·예제/감독/결정 토큰 원장이 자기 CPU 계획과 맞아야 평가에 들어간다.

| 경로 | 계산량과 해석 |
|---|---|
| 공식 base에서 양쪽의 짧은 verifier-only 적응 | 기존 장비의 118회 학습 중앙값 101초·누적 16을 단순 환산하면 약 6초/예제다. 승인 4~16쌍이라면 대략 48~64 예제 노출/arm의 규모이며 모델 적재·checkpoint 시간은 별도다. 검사 전체 능력과 장시간 학습 효과는 시험 범위 밖이다. |
| 공통 독립 부모 1회 학습 후 같은 부모에서 fork | 497장에 대한 단일 통과만 같은 속도로 환산해 약 50분 추가이며 common curriculum이 더 크면 시간이 늘어난다. 잘 적응한 공통 모델에서 음성 교체 효과를 분리할 때 유용하다. 첫 경로의 결과가 공유 워밍업 부재로 해석되거나 승인 쌍이 부족할 때 별도 승인 기준으로 준비한다. |
| 양쪽 실제 102 verifier 요청 | 두 arm에서 BF16과 같은 최대 픽셀·토큰을 사용한다. 기존 official-anchor 실측에서 새 요청 37개는 적재 포함 809초였다. 이를 단순 환산하면 102개는 arm당 약 37분이다. 새 arm 추론의 실측 시간은 CPU preflight에서 예측할 수 없으며 중도 중단 시 각 arm의 로컬 캐시를 재개한다. |

부모·보조 예제 외에 동일한 장면 모델을 다시 생성할 이유가 없어 기존 공식 216장 결과를 재사용한다. 새 102개 재판독 응답은 이전 v2를 재사용하지 않는다. Fold 4는 훈련에서 보호되며 새로 동결된 probe가 없으므로 현재 102개 평가 규모에는 포함하지 않는다.

## 사전 결정 규칙

주지표는 102개 공식 주석 조건에서 엄격한 수락·거절의 정확도다. 파싱 실패·코드 불일치·스키마 오류를 명시 거절과 구분한다. 공식 주석의 부재는 별도 리뷰가 없는 경우 미표기 후보로 취급한다. 두 조건은 같은 후보·공식 기준·장면에서 그룹 쌍체 비교를 한다. 일차 판단은 정확도 +0.03, 그룹 쌍체 95% 구간 하한 양수, 유효 정답 수락 비감소, 잘못된 수락 비증가, 공식 앵커 결과 오경보율 20% 이하, 중대성 4 완전 미탐 비증가다. 이 결과만으로 제출을 결정할 수 있는 공식 정성 점수나 별도 현장 성능은 알 수 없다. 34장 제외 민감도는 별도 진단이며 이 범위에는 기존 102개 중 18개 요청이 남는다. 기존 요청 전체는 검증 20개 그룹에 속한다. 제안기는 이 비교에서 고정하며, 알려진 교차 노출과 기존 개발 진단의 성격을 평가 결과에 함께 표시한다. 마스크와 지표 방향은 두 arm 학습 전에 동결한다. [평가 모듈](../kwater_lab/paired_verifier_ab_score.py)

프로젝트 루트에서 실행한다. 아래 해시 자리는 승인 입력과 CPU 준비에서 확인한 값으로 넣는다.

```powershell
$Python = 'C:/Users/JY/.antigravity_kwater_venv/Scripts/python.exe'
& $Python -m kwater_lab.paired_verifier_ab prepare-contract --approved-review-sha256 APPROVED_INPUT_SHA
$Contract = 'data/fold0-verifier-ab/contract-local.json'
& $Python -m kwater_lab.paired_verifier_ab preflight --contract $Contract --approved-sha256 CONTRACT_SHA --output results/fold0_verifier_ab_preflight.json
```

GPU 담당은 승인·passing preflight·현 로컬 작업 종료를 확인한 뒤 각 단계에 같은 계약 인수를 붙인다. `train --arm A`와 `train --arm B`를 각각 연속 실행하고 2회마다 체크포인트를 저장한다. 장애로 중단됐을 때만 `--resume-from`에 해당 arm의 마지막 유효 체크포인트를 지정한다. B 역시 새 초기화로 같은 단계 그리드를 밟는다. `verify --arm A`, `verify --arm B`를 GPU에서 순차 실행하고, 마지막에 `score --output results/fold0_verifier_ab_scored.json`을 CPU에서 실행한다. 계약, 공식 행 ID와 후보 원문은 로컬 `data/` 경로만 사용한다.

## 승인 후 실제 CPU 결과

승인된 공식 대비쌍은 3쌍이다. 추락 2쌍과 인양 관련 1쌍으로, 양쪽 각각 고유 사진 6장, 누적 1, 2에폭에서 optimizer call 12회 계획이다. 실제 CPU 토큰화에서 감독 답변 790토큰과 결정 가중치 156토큰이 양쪽 일치했다. 시각 토큰은 A 3,968, B 4,264였으며 그 차이는 진단으로 남겼다. 새 사람 검수 없이 승인된 소수쌍 탐색이며 일반화 판정은 보류한다. [CPU preflight 집계](../results/fold0_verifier_ab_preflight.json)
