# Fold 4 8종 탐색용 제출 후보

완료된 2에폭·100스텝 어댑터를 주최자 4B 오프라인 런타임에 연결한다. 개발 Fold 0–3의 791장 중 8코드로 변환할 수 있는 790장이 학습과 사례 검색에 들어간다. 사례 검색 원장은 주최자의 배포 사례에서 790건을 좁혔으며, 참가자 라벨을 주최자 변환기로 처리했을 때와 790건의 내용과 순서가 모두 일치했다. 평가 사진·예측문, 외부 데이터 및 학습 체크포인트를 ZIP에 넣지 않는다. 기존 제출과 다른 어댑터다.

```powershell
$env:CUDA_VISIBLE_DEVICES = '-1'
$env:OMP_NUM_THREADS = '1'
python -B -m kwater_lab.package_fold4_eightcode --zip data/submissions/kwater-fold4-eightcode-20261127.zip
```

주최자 기반 모델, 단일 BF16 GPU, SDPA, 공식 프롬프트와 출력 변환을 사용한다. 배치는 4, 생성 상한은 620토큰, 화소 상한은 393,216으로 Fold 4 원생성 설정과 맞춘다. 윈도우 RTX 3060에서 기존 175장 생성은 2,182초였다. 공식 L4에서 설치와 냉기동을 포함한 200장 1,800초·300장 3,600초는 별도 실측이 필요하다.

Fold 4 전체 175장의 로컬 활성 코드 F1은 0.52162, 정상 오경보는 10/49, 중대성 4 완전 미탐은 32/60이었다. 세 그룹 제외 107장에서는 각각 0.54289, 6/27, 20/39였다. 기존 Public 42.04의 주최자 어댑터와 같은 Fold 4에서 짝지은 비교는 없다. 두 패널 모두 사전 정상 오경보 20% 기준을 넘겨 탐색 후보로 분류한다.

공식 사이트의 내 제출 페이지에서 로컬 ZIP을 선택한 뒤 확인 대화상자에서 제출한다. 사이트는 다중 파트로 저장소에 직접 전송한다. 전송 오류 시 같은 파일을 선택하면 저장된 조각부터 이어가며, 업로드 취소는 진행 중인 전송을 중단한다. 최종 제출 번호와 서버 수신 시간을 내 제출에서 확인한다.

완성 ZIP을 다시 열어 주최자 명세, Linux x86-64·CPython 3.12 오프라인 wheel 5개, 최종 어댑터 SHA-256 및 유지한 기준 ZIP 파일들의 크기·CRC를 확인했다. ZIP의 실제 `main.py`에서 GPU 생성 호출을 기존 Fold 4 원생성 175행으로 대체해 재생했다. 공식 8종 파서는 174행을 수용했고 기존 정상 폴백 1행을 포함한 최종 출력은 공식 검사 175/175를 통과했다. 같은 790개 사례를 사용한 독립 변환과 ID 치환 외의 모든 결과가 일치했다. 새 GPU 실실행과 ZIP 전량 공식 키트 추출은 미수행이다.
