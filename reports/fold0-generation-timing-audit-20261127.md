# Fold0 생성 시간과 비교 조건

## RTX 3060에서 실측한 공식 10장

기존 공식 모델은 10장에 2,035.436초가 걸렸고, 생성 루프 계측은 누적 90.0초였다. 체크포인트 shard 로그에서 첫 파일 완료까지 339.27초, 두 파일 완료까지 약 414.4초가 기록됐다. 나머지 약 1,531초는 해당 로그에서 프로세스 시작, 가중치 및 어댑터 초기화, 실행 대기, 후처리로 분리할 수 없다. 생성 첫 장은 26.9초, 일곱 번째 장은 앞 장 대비 19.9초, 나머지는 대체로 5–6초였다. GPU 시스템 최고 사용량은 11,831MiB였다. 10장 중 무위험 출력이 8장이어서 이 속도를 216장의 확정 소요 시간으로 쓰기 어렵다. [기존 실측 집계](../results/official_baseline_10.json)

공식 배치는 소스의 설명 문자열에 8로 적혀 있지만 실제 `KW_BATCH` 기본값은 16이다. 10장 실측과 현재 RTX 3060 Fold0 실행기는 1을 명시한다. 공식 기준의 900토큰과 원본 파서·포맷터는 유지했다. 기준 생성은 여러 재개 배치를 같은 프로세스에서 처리하며 모델을 한 번만 로드한다. 다시 시작하면 완료 배치를 재생한다. 모델 로드, 생성, 입력·가중치 검증 시간은 새 실행 요약에서 분리한다. [기준 실행기](../kwater_lab/fold0_official_resume.py)

## 기준 모델·후보·제출 코드 비교

| 실행 | 기반 가중치 모드 | 최대 이미지 픽셀 | 인식 생성 상한 | 시각 확인 생성 상한 | 배치 |
| --- | --- | ---: | ---: | ---: | --- |
| 공식 기준 | BF16 | 393,216 (`384 × 32²`) | 900 | 별도 확인 없음 | 공식 기본 16, 3060 비교에서는 1 |
| Fold0 11코드 후보 | BF16 우선, OOM 시 별도 NF4 기록 | 524,288 (`512 × 32²`) | 620 | 320, 기본 primary 비교에선 생략 | 3060 실행기 1 |
| 11코드 제출 템플릿 | BF16 | 524,288 | 620 | 하이브리드 활성 시 320 | 기본 4, 패키징 인수로 지정 가능 |

후보는 작은 위험 근거를 볼 수 있도록 입력 상한을 33% 늘린 기존 실험 설정을 유지한다. 620·320토큰 상한은 11코드 후보의 제한된 JSON 형식과 검증 응답을 전제로 한다. 상한에 도달한 출력은 끝의 JSON 괄호 누락, 긴 사진 근거 생략, 유효한 무위험 출력과 구별되는 파싱 실패를 확인해야 한다. Fold0는 원문 파싱·엄격한 내부 스키마·공식 결과 스키마를 각각 기록한다. 상한을 줄이거나 배치를 올렸을 때 속도와 품질이 그대로 유지된다는 GPU 실측은 없다. 기준과 후보의 대응 차이에는 모델·프롬프트·해상도·생성 예산이 함께 반영된다. [후보 평가](../kwater_lab/hybrid_pipeline.py) · [ZIP 생성기](../kwater_lab/package_submission.py)

제출 코드와 후보 평가가 동일한 픽셀·토큰 상수를 사용하도록 연결했다. RTX 3060에서 가능한 BF16 배치 1로 비교한 경우에도 제출 기본 배치 4의 L4 실측은 별도이며, 배치 일치가 필요하면 패키저도 `--batch-size 1`로 지정한다. 스크립트는 각 출력 SHA-256과 맞는 양쪽 실행 요약에서 정밀도·픽셀 상한·토큰 상한·배치를 읽어 216장 대응 집계에 기록한다. [대응 비교기](../kwater_lab/fold0_production_compare.py)

후보의 보조 zero-shot 실행이나 중단 후 재개 때 기존 216장 FT 원문 캐시가 완전하면 FT 가중치를 다시 올리지 않는다. 캐시 검사에는 입력 순서, 이미지 SHA-256, 실제 VLM 코드 해시, 프롬프트, 모델 설정을 포함시켰다. 이전에는 순서가 있는 배치임에도 입력 순서를 무시하고, 데코레이터 래퍼 파일의 해시가 실제 VLM 코드 해시로 기록될 수 있었다. CPU 회귀 검사에서 완전 캐시는 가중치 로드 없이 재생되고 입력을 뒤집으면 거절되는 것을 확인했다.

CPU 전용, BLAS·OMP 1 스레드에서 전체 단위 테스트 78개를 통과했다. 출력 파일이 LF에서 CRLF로 바뀌면 대응 집계가 원본 설정 증명을 거절하는 것도 확인했다. PowerShell 실행기는 문법 검사에 통과했다. Linux GPU 실행과 절감 시간 실측은 이번 검증에 포함되지 않았다.

## 사건별 중간 확인

기존 36장 패널은 각각 다른 사건의 최소 salted SHA-256 사진을 사용한다. 현행 manifest 순서에서는 처음 54장, 108장, 162장까지 각 14장만 포함되고, 마지막 패널 사진은 216번째다. 임의의 앞부분에는 이 패널의 정의를 적용할 수 없다. 현재 실행에서는 저장 배치 수와 포맷 상태를 중간에 확인하고, 공식 대응 집계는 양쪽 216장 검증 뒤에 계산한다. 새 배치 1 실행을 별도로 기획한다면 대상과 순서를 실행 전에 고정해 패널 36장을 앞에 둘 수 있다. 양쪽에서 동일하게 적용하고 새로운 캐시를 사용해야 하며, 그때의 36장 값은 지정 패널 중간 확인용이다. 이번 작업에서는 실행 순서를 변경하거나 중간 성능 점수를 생성하지 않았다.
